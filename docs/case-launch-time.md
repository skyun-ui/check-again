# 사례: 시작 속도 — 가설을 버리고 측정으로 찾은 진짜 원인

## 증상
"위젯을 누르면 바로 앱으로 안 가고 살짝 딜레이가 있는 느낌"이라는 사용자 피드백.

## 첫 가설: 개발용(Debug) 빌드라서 느리다
그때까지 기기에는 늘 Debug 빌드를 설치했다. 최적화가 꺼져 있으니 그럴듯한 가설이었다. 하지만 추측으로 고치지 않고 먼저 쟀다.

## 측정 방법
앱 시작 시각을 기준으로 단계마다 경과 시간을 남기는 로그를 넣었다.

```swift
enum LaunchTiming {
    static let start = Date.now
    static func mark(_ step: String) {
        logger.info("\(step): \(Int(Date.now.timeIntervalSince(start) * 1000))ms")
    }
}
```

`저장소 준비 → 알림 준비 → 캘린더 준비 → 화면 구성 시작 → 목록 계산 → 첫 화면` 순서로 찍고, 시뮬레이터와 실기기에서 Debug/Release를 각각 여러 번 실행했다.

## 결과

| 환경 | 저장소 준비 | 첫 화면 |
|---|---|---|
| 시뮬레이터 Debug | 약 0.05~0.09초 | 약 1.7~2.5초 |
| 시뮬레이터 Release | 약 0.05~0.1초 | 약 1.6~2.3초 |
| **실기기 Debug** | **약 0.02초** | **약 0.1초** |
| **실기기 Release** | **약 0.02초** | **약 0.1초** |

- 시뮬레이터의 긴 시간은 앱 설정이 끝난 뒤 첫 화면 구성이 시작되기까지의 구간에 몰려 있었다. 우리 코드 밖, 시뮬레이터가 창을 준비하는 시간이다.
- 실기기에서는 Debug와 Release 모두 0.1초. **가설은 틀렸다.**

## 진짜 원인
로그를 다시 보니, 첫 화면(목록 모음)이 0.1초에 뜬 뒤 "마지막으로 본 화면" 설정 때문에 **보던 목록으로 옆으로 밀려 들어가는 화면 전환**이 이어지고 있었다. 화면이 한 번 바뀌는 그 과정이 "살짝 딜레이"로 느껴진 것이다.

## 수정
`onAppear`에서 경로를 바꾸던 것을, 앱 시작 시점에 저장소에서 마지막 화면을 계산해 내비게이션을 **처음부터 그 경로로 시작**하게 했다. 전환 애니메이션이 사라졌다.

```swift
// 앱 시작 시: 설정(마지막으로 본 화면 / 전체 / 목록 모음)과 저장된 마지막 화면으로 경로 계산
initialPath = LaunchScreen.initialPath(setting: setting, lastScreen: lastScreen, lists: lists)
// 첫 화면은 그 경로로 바로 시작
ListsHomeView(initialPath: initialPath)
```

## 덤으로 발견한 것: Release 빌드가 컴파일되지 않았다
Debug와 Release를 비교하려고 처음으로 Release 빌드를 만들었더니 **빌드가 실패했다.** Xcode 프리뷰(`#Preview`) 코드가 Debug 전용 샘플 데이터를 참조하고 있었다. 늘 Debug만 설치해서 아무도 몰랐던 문제다. App Store 제출 직전에 발견했다면 훨씬 곤란했을 것이다. 프리뷰를 `#if DEBUG`로 감싸 고쳤고, 이후 기기에는 Release 빌드를 설치한다.

## 배운 점
- 그럴듯한 가설일수록 먼저 잰다. 측정이 가설을 기각했고, 진짜 원인은 성능이 아니라 화면 흐름이었다.
- 시뮬레이터 숫자는 실기기와 크게 다를 수 있다. 사용자가 느끼는 건 실기기다.
- 평소에 쓰지 않는 경로(Release 빌드)는 깨져 있어도 모른다. 출시 경로는 일찍, 자주 확인한다.
